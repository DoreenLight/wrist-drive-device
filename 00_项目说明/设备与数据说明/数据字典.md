## 1. 数据分两类

| 类别 | 命令码 | 内容 | 方向 |
|---|---|---|---|
| **IO 参数** | `0x01` `IO_WRITE` | 开关、模式选择等 1 字节控制量 | 上位机 → 设备 |
| **浮点参数** | `0x02` `FLOAT_WRITE` | 角度、速度、增益等 4 字节浮点数 | 双向 |

设备上传的遥测（`0x81 TELEMETRY`）用的就是**同一套浮点参数 ID**，
即"某个 ID 的值"既可能是上位机设下去的，也可能是设备测上来的。

| `0x08` | M1 康复启停 | `1`=启动，`2`=停止 | 启动/停止 M1 **被动康复** | 康复页 Motor1 →「被动」选项卡 → `▶ 启动 / ■ 停止` |
| `0x09` | M2 康复启停 | `1`=启动，`2`=停止 | 启动/停止 M2 **被动康复** | 康复页 Motor2 →「被动」选项卡 → `▶ 启动 / ■ 停止` |

### 3.1 电机 1（M1）

|---|---|---|---|---|---|
| `0x01` | M1 轨迹输入 | ° | 双向 | 下发给 M1 的目标角度（PID 设定值）；设备上传时即为轨迹指令值 | 决定 M1 要转到哪个角度 |
| `0x02` | M1 反馈角度 | ° | 双向 | 上行：IMU 实测的 roll 角；下行：M1 速度目标 | 上行用于观察实际角度；下行用于设定速度 |
| `0x03` | M1 PID 输出 | — | 双向 | 上行：PID 控制器的输出量；下行：电流目标 | 上行用于观察控制量是否饱和；下行设定电流 |
| `0x04` | M1 Kp | — | 双向 | PID 比例增益 | 调节位置/速度环响应强度 |
| `0x05` | M1 Ki | — | 双向 | PID 积分增益 | 消除稳态偏差 |
| `0x06` | M1 PWM 占空比 | ±1.0 | 双向 | 输出到电机的 PWM 占空比 | PWM 测试模式下直接给定占空比 |
| `0x07` | M1 最大速度 | °/s | 双向 | 运动速度上限 | 限制 M1 运动速度 |
| `0x08` | M1 康复最小角度 | ° | 双向 | 被动康复轨迹下限 | 设定 M1 被动康复行程 |
| `0x09` | M1 康复最大角度 | ° | 双向 | 被动康复轨迹上限 | 设定 M1 被动康复行程 |
| `0x0A` | M1 康复循环次数 | — | 双向 | 往复次数 | 设定 M1 被动康复做多少个来回 |
| `0x0B` | T 波虚拟轨迹 | ° | 双向 | 被动康复的虚拟往复轨迹值 | **康复曲线**上作为指令基准显示，与实际角度对比 |
| `0x0C` | M1 主动极限角 1 | ° | 双向 | 主动康复一侧边界 | 限定主动运动范围 |
| `0x0D` | M1 主动极限角 2 | ° | 双向 | 主动康复另一侧边界 | 限定主动运动范围 |
| `0x0E` | M1 主动停顿时间 | s | 双向 | 到达极限角后停留时间 | 控制康复节奏 |
| `0x0F` | M1 主动 Tmax | N·m | 双向 | 主动康复的**力矩出发门槛** | `\|Mx\| ≤ Tmax` 时轨迹不动；超出部分才产生运动（✅ 固件已验证） |
| `0x10` | M1 主动刚度 k | (N·m)/(deg/cycle) | 双向 | **力矩→速度的换算系数** | 速度 = (`\|Mx\|`−Tmax) ÷ k；k 越大同样力矩走得越慢，即越“硬”（✅ 固件已验证） |

> ⚠️ **`0x0B` / `0x1D` 是一个「读写语义不同」的重载 ID（实测确认）**
>
> | 方向 | `0x0B` 的含义 | `0x1D` 的含义 |
> |---|---|---|
> | 上行（设备→上位机） | **T 波虚拟轨迹值**（当前虚拟往复角度，单位 `°`，范围 = 极限角1…极限角2） | M2 T 波轨迹值 |
> | 下行（上位机→设备） | **T 波速度**（`°/s`），来源：界面「主动 · `T波速度`」输入框 | M2 T 波速度 |
>
> 因此：
> - **不能把上行值当作“速度”看**（它是一条随时间往复的轨迹，不是常量）；
> - **不能把下行写入的值与随后读回的值直接对比**（两个量纲）；
> - 实测证据：`02_采集数据/telemetry/telemetry_20260727_164733.csv` 中 `T波虚拟轨迹` 为 ±30.000°
>   的干净三角波；而另外两份历史 CSV 中它**恒为 0**（那两次未跑主动康复）。
> - 开发注意：`mainwindow.cpp` 中该输入框的界面标签是 `T波速度(°/s)`，但写入的浮点 ID 是 `0x0B`，
>   而 §3.1 表中 `0x0B` 的名字是「T 波虚拟轨迹」——这不是文档笔误，是固件层面的 ID 复用。

### 3.4 重点辨析：M1 「轨迹输入」与「反馈角度」

这两个值是 M1 闭环控制里最核心的一对，也是最容易混淆的一对。

| 项目 | 轨迹输入（`0x01`） | 反馈角度（`0x02`） |
|---|---|---|
| 源码注释 | `// PID 设定值` | `// roll IMU 实测` |
| 控制术语 | **设定值（Setpoint / 指令）** | **实测值（Measurement / 反馈）** |
| 通俗理解 | **"想去多少度"** | **"实际在多少度"** |
| 数据来源 | 上位机下发的「角度目标」，或 MCU 内部生成的康复轨迹 | MCU 读取 **IMU 的 roll 轴角度** |
| 单位 | 角度 °（字典单位字段留空，但界面占位符与曲线均为角度） | ° |
| 方向 | 双向：既可下发，也随遥测上传 | 双向：上行是实测角，下行被用作「速度目标」 |

#### 二者构成一个闭环（轨迹输入是独立输入，**不由反馈角度算出**）

```text
   ┌── 轨迹输入 (0x01) ── 独立规划、按时间推进
   │                      · 康复时由 MCU 按你填的参数生成
   │                      · 手动扳时由上位机「角度目标:」写入
   ▼
 偏差 = 轨迹输入 − 反馈角度      ← 控制内环偏差（🔶 推断，不是界面上的那个“误差”）
   │
   ▼
 PID 运算 ──→ PID 输出 (0x03) ──→ 电机 ──→ 实际转动
   ▲                                            │
   └────── 反馈角度 (0x02) ←── IMU 实测 ←──┘
```

**关键点：箭头只从「反馈角度」进入“比较环节”，不会回到「轨迹输入」。**

如果轨迹输入由反馈角度算出来，那偏差恒为 0，PID 永远不会动作，
整个闭环就退化成“自己追自己”。所以设计上它必须是**独立输入**。
（如果用真实数据验证？见 §3.6 的 86.3% 符号一致与 §3.7。）

- **轨迹输入**是 PID 要追的目标；**反馈角度**是被控量的实际值；
- 两者之差就是**跟随偏差**。曲线里两条线的间距越大，说明电机越跟不上指令
  （可能原因：速度上限太低、Kp/Ki 不合适、负载过大、限位受阻）；
- 康复页的「Motor1 轨迹跟踪」图把这个闭环直接画出来：
  目标轨迹 = `0x01 轨迹输入`、实际轨迹 = `0x02 反馈角度`，
  还可勾选叠加下位机上传的 `0x0B` 原始曲线，
  用来直观对比「指令轨迹 ↔ 实际角度 ↔ 下位机原始轨迹」。

#### 界面上的坑：康复页「M1 角度」显示的不是反馈角度

| 界面位置 | 实际显示的 ID |
|---|---|
| 康复页「实时状态」→ `M1 角度:` | **`0x01` 轨迹输入**（指令值，不是实测值） |
| 电机页「Motor1 数据」第一格 `轨迹输入` | `0x01` |
| 电机页「Motor1 数据」第二格 `反馈角度` | `0x02` |

要看**真实角度**请到电机页看「反馈角度」，或在康复页「Motor1 轨迹跟踪」图里看实际轨迹线。

#### ⚠️ 同一个 ID，上下行语义不同

`0x02` 这个编号被两个不同物理量共用：

| 方向 | 语义 | 对应界面 |
|---|---|---|
| 上行（设备→上位机） | **M1 反馈角度**（IMU 实测，°） | 「Motor1 数据」第二格、轨迹跟踪图实际轨迹 |
| 下行（上位机→设备） | **M1 速度目标** | Motor1 面板「速度目标:」输入框 |

所以「速度目标」里填的值不会让「反馈角度」立刻变成那个数——它们只是共用 `0x02` 这个编号。
同理 `0x03` 上行是「PID 输出」、下行是「电流目标」。

### 3.5 参考角度（参考轨迹）与轨迹输入的区别

康复页「轨迹跟踪」图里一共有三条数据曲线，其中容易混淆的是**参考轨迹**和**轨迹输入**：

| 颜色 / 图例 | 是什么 | 对应 ID |
|---|---|---|
| 🟢 **参考轨迹** | 上位机**本地生成**的理想往复轨迹 | 无（不占用任何 ID） |
| 🔵 **轨迹输入** | 下位机实际上传的**目标指令** | `0x01`（M1）/ `0x11`（M2） |
| 🟠 **反馈角度** | 下位机实际上传的**实测角度** | `0x02`（M1）/ `0x12`（M2） |

#### 参考角度是怎么算出来的

参考轨迹完全由**上位机本地计算**，不依赖下位机：

```
参数（从「主动」选项卡只读获取）：T波速度 / 极限角1 / 极限角2 / 停顿时间
+ 周期数（轨迹跟踪区自己的输入框，1~20）
        ↓  makeRefTrajectory()
一条分段线性三角波：
   保持(极限角1, 停顿) → 斜坡到极限角2 → 保持(极限角2, 停顿) → 斜坡回极限角1
        ↓  refValueAt(t) 沿折线线性插值
时刻 t 的参考角度
```

- 单周期时长 = `2 × 停顿 + 2 × (极限角2 − 极限角1) / T波速度`
- 总时长 `T = 周期数 × 单周期`，X 轴就是 `[0, T]` 秒
- Y 轴自动取 `[min(极限角1,极限角2)−5, max(极限角1,极限角2)+5]`

#### 与轨迹输入的四个关键区别

| 维度 | 🟢 参考角度 | 🔵 轨迹输入（`0x01`/`0x11`） |
|---|---|---|
| **谁生成** | 上位机本地计算 | 下位机 MCU 生成 |
| **是否下发** | **不下发**，纯本地绘图 | 是真实控制指令，已生效 |
| **数据来源** | 参数表 + 折线插值 | 遥测帧上传 |
| **设备离线时** | 依然完整可见 | 无数据 |

#### 为什么需要一个参考角度（不直接用轨迹输入当基准）

根本原因：**只看「轨迹输入 vs 反馈角度」分不清误差出在谁身上**。有了参考轨迹就能把误差拆成两段：

```
参考轨迹 ——(①)——→ 轨迹输入 ——(②)——→ 反馈角度
            ① 下位机轨迹生成的偏差      ② 电机跟随的偏差

①  差异大  →  参数不一致 / 下位机未启动 / 固件限幅或时序与预期不同
②  差异大  →  PID 不合适 / 速度上限偏低 / 负载过大 / 撞限位
```

四条现实理由：

1. **分离误差来源**：拆成“指令生成偏差”与“执行跟随偏差”，定位问题才有方向；
2. **离线也能看基准**：打开页面即可预览完整期望波形，不需要设备在线；
   设备没启动、`0x01` 不变时，绿线仍在，一眼就能看出“下位机没在执行”；
3. **不依赖不可靠的上传值**：下位机 `0x0B`/`0x1D` 原始轨迹在当前链路上会夹杂损坏值
   （代码里因此做了 `|angle| > |极限角|×1.5` 的过滤并计数），参考轨迹不受此影响；
4. **安全且可复现**：纯本地绘图，**不调用任何 send* 下发函数**；
   同一组参数永远得到同一条绿线，不同实验批次可直接对比。

#### ⚠️ 读数行里的「误差」不是目标减实测

图中读数行的含义（源码 `updateTrackerViews()`）：

```
t = 当前/总时长 s　参考 X°　目标 Y°　实测 Z°　误差 E°
```

其中 **`误差 = 参考 − 实测`**（不是 `目标 − 实测`）——因为参考轨迹才是可信基准。

> 参考轨迹的参数取自各电机「主动」选项卡，且**只读使用**：
> 改这些输入框不会下发任何指令；实验开始后也不允许改变本轮参考轨迹。

### 3.6 三层结构与两个「误差」

把三个量放到一起看，才不会混：

```
① 参考轨迹（绿线）    上位机本地算     纯标尺，不下发     ← “我以为应该这样动”
② 轨迹输入 (0x01/0x11) 下位机 MCU 生成   真正的设定值       ← “设备决定要这样动”
③ 反馈角度 (0x02/0x12) IMU 实测                         ← “手腕实际上在哪”

控制内环（MCU 内部）：PID 用 (② − ③) 算输出 → PID 输出(0x03) → 驱动电机
界面显示误差：① − ③（仅是评价指标）
```

#### 两个「误差」必须分开看

| 名称 | 公式 | 在哪里算 | 作用 | 证据等级 |
|---|---|---|---|---|
| **控制内环偏差** | `② − ③`（轨迹输入 − 反馈角度） | MCU 内部 | 喂给 PID，**决定电机出力** | 🔶 推断（固件源码不可见；📊 实测 86.3% 符号一致） |
| **界面显示误差** | `① − ③`（参考轨迹 − 反馈角度） | 上位机 | **评价指标**，给人看“期望 vs 实际” | ✅ 已验证（`updateTrackerViews()`） |

> ⚠️ **命名更正**：本文早前版本曾把 `② − ③` 直接叫作“误差”，容易被误认为界面上那个数。
> 现统一叫法：
> - `② − ③` → **控制内环偏差**（推断值，界面上不显示）
> - `① − ③` → **界面显示误差**（唯一被显示出来的“误差”）

> ⚠️ 看到显示误差 2.4° 时，电机可能正在完美地跟踪它自己的 ② ——
> 两个数字说的不是同一件事。判断电机性能请看 **② 与 ③ 贴不贴**。

#### 为什么必须有「下位机自己生成的 ②」

因为电机要出力就必须有“要去哪儿”的目标，而这个目标**每个控制周期都要更新**，
上位机给不了这个更新率：

| 靠上位机会怎样 | 后果 |
|---|---|
| Windows 定时是毫秒级且抖动 | 设定值一顿一顿 → 电机一顿一顿 |
| 串口有误码（本链路实测存在大量损坏帧） | 丢一个设定值，电机卡在上一位置 |
| USB 一拔 | 上位机没了，电机不知道停在哪、怎么停 |

主动康复更是必须有 ②：设备要判断“你偏离目标多少、使了多大力”才能决定给助力还是阻力 ——
**没有 ②，就没有“偏离”的基准**。

#### ② 的形状由什么决定

完全由你在界面上填的参数决定（这也是你唯一能“间接控制” ② 的方式）：

| 模式 | 决定 ② 形状的参数 |
|---|---|
| 被动康复 | 最小角度 `0x08`、最大角度 `0x09`、循环次数 `0x0A`、最大速度 `0x07`（限速） |
| 主动康复 | **不是按参数规划，而是被力矩推动**：Tmax `0x0F`（门槛）+ 刚度 k `0x10`（把超限力矩换算成速度）；T 波参数只决定遥测里那条绿线 |
| 手动/调试 | 电机页「角度目标:」直接写 `0x01`，定点定位 |

#### ⚠️ ① 和 ② 本来就不是同一条曲线（实测）

基于 `02_采集数据/telemetry/telemetry_20260727_164733.csv`（716 帧）实测：

| 检查项 | 实测值 |
|---|---|
| 平均采样间隔 | 0.053 s |
| ② 轨迹输入变化率 | 约 **2.57 °/s** 平滑推进 |
| `0x0B` T 波轨迹 | 在 **±30°** 之间快速摆动（相邻样本即跳几十度） |
| 平均 `\|② − ③\|` | **1.51°**（跟踪很好） |
| 平均 `\|② − T波\|` | **25.61°**（差异极大） |
| PID 输出正负 与 `(②−③)` 同向 | **86.3%**（\|偏差\|<0.3° 的 11.2% 不计，矛盾仅 2.5%） |

结论：

1. **② 是设备真正在执行的一条平滑规划轨迹，不是 T 波的直接复制**；
2. **PID 确实由 `(② − ③)` 驱动**（86.3% 符号一致 + 上述片段反例均可验证）；
3. 因此当 ①（你自己设的三角波）与 ②（设备实际轨迹）不是同一条时，
   **显示误差偏大是正常的，它反映的是参数/模式不匹配，而不是电机性能差**。

#### ✅ 已由固件确认（2026-10-20 更新）

② 的**具体生成算法**（怎么插值、怎么限速、会不会参考实测值做平滑）只有固件代码能看到。
PC 端能确定的只有两件事：

1. 你下发的参数确实在影响 ②；
2. ② 与 ③ 的差确实在驱动 PID 输出。

本文早前关于“开环规划、不看反馈”的描述**只对被动/手动模式成立**；
主动康复的完整机制已在下位机源码 `universal-joint-rehab-system` 的
`Order_Creat_process()` 中确认，详见 §3.7。

#### 主动康复里的「跟随 vs 抵抗」由什么决定

同样一个“手带动机器”的动作，手感可能是“几乎无阻”也可能是“明显较劲”，
决定因素是 **刚度 k（`0x10` / `0x24`）**：

| 刚度 k | 设备行为 | 感受 |
|---|---|---|
| 很小 | 同样超限力矩 ÷ k → 速度很大 | 接近随动，你带着它走 |
| 很大 | 同样超限力矩 ÷ k → 速度很小 | 像在推一个很硬的旋钮 |

再加上力上限 **Tmax（`0x0F`）/ Fmax（`0x23`）** 封顶，
所以**设备是“随动”还是“抵抗”，是参数决定的，不是硬件决定的**。

### 3.7 「轨迹输入」会不会由反馈角度或刚度算出来？

> ⚠️ **本节已根据下位机固件源码重写（2026-10-20）。**
>
> 早前的结论“轨迹输入不依赖反馈与刚度”**只对被动/手动模式成立**，
> 对**主动康复**完全相反。

**答案取决于当前模式**：主动康复里它确实由 **力矩反馈 + Tmax + 刚度 k** 算出来；
被动/手动里它是一条独立的限速规划曲线。详见下方三条路径。

| 常见推测 | 实际情况 |
|---|---|
| 轨迹输入 = f(反馈角度, 刚度 k, …) | ❌ 轨迹输入是**独立规划**的，按时间推进 |
| 刚度 k 决定轨迹输入长什么样 | ❌ 刚度 k 作用在**输出力/力矩**上，不改轨迹 |
| 设备先“决定助力还是阻力”，于是产生不同轨迹 | ❌ 轨迹始终同一条；**助力/阻力取决于你相对轨迹超前还是落后** |

#### 刚度 k 到底作用在哪一步

```text
轨迹输入 ──(−)── 偏差 ──(× 刚度 k)── 期望力 ──(受 Tmax/Fmax 封顶)── 实际出力
                    ▲
                反馈角度

**主动康复的真实算法（`main.c` 的 `Order_Creat_process()`，100 Hz）**：

```c
mx   = DR304[3];                                  // Mx 力矩 (N·m)
tmax = motor1_get_actv_tmax();
k    = motor1_get_actv_stiffness();

if (fabsf(mx) > tmax)
    motor1_sudu = -sign(mx) * (fabsf(mx) - tmax) / k;   // 超限力矩 ÷ k = 速度
else
    motor1_sudu = 0.0f;                                 // 未超门槛 → 轨迹冻结

m1_traj_current += motor1_sudu * 0.01f;             // 速度积分成位置
Control_P_PID.In_val = m1_traj_current;             // ← 这就是 0x01 轨迹输入
```
```

#### 助力还是阻力：不是模式开关，而是偏差符号

| 你相对轨迹的位置 | 偏差符号 | 设备出力方向 | 主观感受 |
|---|---|---|---|
| **落后**于轨迹（轨迹 > 实测） | 正 | 往前推你 | **助力** |
| **超前**于轨迹（轨迹 < 实测） | 负 | 往后阻你 | **阻力** |
| 刚好在轨迹上 | ≈ 0 | 只保持姿态，不出额外力 | 无感 |

📊 **实测佐证**（`telemetry_20260727_164733.csv`，716 帧）：
PID 输出正负与 `(轨迹输入 − 反馈角度)` 同向 **86.3%**，矛盾仅 2.5%。

```text
16:48:07.9   轨迹 25.089   反馈 22.945（落后）→ PID 输出 +0.211（往前推）
16:48:08.7   轨迹 20.496   反馈 23.427（超前）→ PID 输出 −0.047（往后阻）
```

#### 📊 「轨迹输入到底根据什么来」的三条硬证据

同一份数据（716 帧、采样间隔 53 ms）做了三个独立检验：

| 检验 | 结果 | 结论 |
|---|---|---|
| `corr(轨迹输入, T波轨迹 0x0B)` | **−0.023** | 几乎零相关 → **轨迹不是 T 波的复制** |
| 滞后相关峰值（−40…+40 样本扫） | 滞后 **+9 样本 ≈ 477 ms**，corr **+0.998** | **轨迹领先反馈 477 ms** → 轨迹是“源”、反馈是“果” |
| 反例窗口 16:47:53（约 1 s） | 轨迹**恒为 0.049**，而反馈从 −9.76 升到 −1.72 | **轨迹不随反馈变化** |

**一致性交叉验证**：采样间隔 53 ms、轨迹速率 2.57°/s → 每样本移动 0.136°；
×9 样本 ≈ **1.22°**，与实测平均差 **1.51°** 吐合——说明那 477 ms 滞后就是跟随误差。

> **固件确认的结论**：
> - **主动康复**：轨迹输入 = 由 `Mx 力矩 + Tmax + 刚度 k` 积分而来 → **确实依赖力反馈与刚度**；
> - **被动康复 / 手动**：轨迹输入 = 由 `目标角度 + 最大速度 + 固定加速度 0.1°/周期²` 限速规划而来 → 不依赖角度/力反馈；
> - **两种模式下 T 波（`0x0B`）都不参与** 轨迹输入的生成，只用于遥测显示。
> 它是 MCU 内部按“界面参数 + 内部时间”独立生成的位置曲线。
> 若真由反馈算出，滞后相关峰值应出现在**负滞后**（反馈领先），而实际正好相反。

#### 🔶 必须保留的不确定性

若固件采用**导纳型**实现（参考位置被外力推动），则“轨迹”确实会随你的用力和实际位置而移动。
PC 端只能看到两个侧面证据：

- M2 需要选 `Fy` / `Fz` 作为力闭环方向 → 固件确实在用力传感器；
- 参数里有 `刚度 k` + `Tmax/Fmax` → 更像**阻抗型**（位置偏离 → 出力）。

**现已由固件确认为导纳型（力顺应）**：不是“位置偏差 → 出力”，
而是“力矩超限 → 转成速度 → 积分成位置设定值”，位置环再去跟随这个被推动的设定值。

> 相关问答：`术语与名词.md` 第 5.5 节 Q2 / Q6。

参数来源：参考轨迹的 4 个参数**复用**现有「主动」选项卡的输入框
（`0x0B` `0x0C` `0x0D` `0x0E`），**不会**因为“开始实验”而把这些参数下发到设备。

参考轨迹公式（与下位机 T 波波形一致的分段线性三角波）：

```text
单周期 = 停顿 + (极限角2 − 极限角1)/T波速度 + 停顿 + (极限角2 − 极限角1)/T波速度

```

### 4.4 关于「运行: 00:00:00」

康复页「实时状态」中的运行计时**恒为 `00:00:00`**：计时器 `treatTimer` 创建后未启动，
且 `treatRunning` 从未置为 `true`。这是**已知限制，不是故障**，不影响康复与记录功能。

## 5. 遥测数据流与刷新机制

```text
MCU 周期上传 TELEMETRY 帧
        ↓  串口
ProtocolWorker 线程：解析帧 → 校验 → 取出 [ID, 浮点值] 列表
        ↓  跨线程信号 telemetryReceived
主线程 onTelemetryReceived()
        ├─ 若正在记录 → 追加到内存缓冲（含毫秒时间戳）
        ├─ 推入队列 mTelemetryQueue
        ├─ 立即刷新：遥测表格 / 康复页标签 / 六维力标签
        └─ 曲线刷新：由 50 ms 定时器批量取队列、合并后喂给 4 个曲线控件
             ├─ 电机页 Motor1 曲线、Motor2 曲线
             └─ 康复页 Motor1 曲线、Motor2 曲线
```

要点：

- **曲线是 50 ms 批量刷新**的，多帧合并时**同 ID 取最后一帧**；
  因此曲线是"降采样后的趋势图"，**不等于原始逐帧数据**，做精确分析请用 CSV。
- 曲线纵轴**默认**为 `-5 ~ +5`；但只要该图上有一个曲线可见，下一次刷新就会按可见曲线的
  数据范围**自适应重设 Y 轴**（上下各留 15% 余量），所以实际看到的是自动缩放，不是固定 `-5 ~ +5`。
  四张图的曲线默认**全部隐藏**（需要勾选复选框），此时 Y 轴才停在 `-5 ~ +5`。
- 曲线 X 轴用的是**刷新计数**（每次刷新 +1），不是秒；窗口宽度固定 200 个刷新周期
  （约 10 s）。因此**现有曲线不能当作时间轴使用**。
- 每个 series 的缓存上限为 **200 点**，超出丢弃最旧点。
- 遥测表格显示 2 位小数；曲线不做数值标注。

### 5.1 轨迹跟踪视图的改动（✅ 已实现）

康复页两张图已改成「固定参考轨迹 + 时间游标 + 当前点」，因此上面三条机制对这两张图不再适用，改为：

1. **真实时间轴**：X 轴是以秒为单位的 `[0, T]`（T = 周期数 × 单周期），不再是刷新计数；
2. **原始样本通道**：实时点携带「该值的接收时间戳」（`feedTrackerSample()`），
   不复用「同 ID 取最后一帧」的合并结果，避免点画在错位的时间上（最大偏差 = 50 ms × 批内帧数）；
3. **数值合理性过滤**：丢弃非有限值、或 `|angle| > |极限角| × 1.5` 的样本并计数（读数行显示「丢弃异常 N」）。
   原因是设备当前上传的遥测帧存在损坏（见 `需求_轨迹跟踪视图改造.md` §6.1），
   `0x12`（M2 实际位置）落在损坏区间。

电机控制调试页的两张图仍用上面 50 ms / 200 点 / Y 轴自适应的旧机制；
CSV 记录（下一节）**不受**这些改动影响。

## 6. CSV 记录文件格式

由康复页的 `● 开始记录` / `■ 停止记录` 生成。

| 项目 | 说明 |
|---|---|
| 触发方式 | 点 `● 开始记录` 只在内存缓冲；**点 `■ 停止记录` 才一次性写盘** |
| 文件名 | `telemetry_YYYYMMDD_HHmmss.csv`（时间取**开始记录**的时刻） |
| 保存位置 | **exe 所在目录**（即 `build/Desktop_Qt_6_8_2_MinGW_64_bit_Release/`），不是 `02_采集数据/` |
| 时间列 | 第一列 `时间`，格式 `hh:mm:ss.zzz`（精确到毫秒） |
| 数据列 | **只包含本次记录中实际上传过的 ID**，按首次出现顺序排列 |
| 列名 | 取参数名称（如 `M1 轨迹输入`）；字典中没有的 ID 写作 `0x??` |
| 数值格式 | 定点 3 位小数 |
| 缺值 | 某帧没有该 ID 时**留空**（不会填 0） |
| 编码/换行 | UTF-8，LF |

**示例**（列取决于实际上传的 ID）：

```csv
时间,M1 轨迹输入,M1 反馈角度,M2 规划位置,Fx,Fy,Fz
09:12:31.004,0.000,0.512,12.300,0.120,-1.450,0.030
09:12:31.024,0.000,0.518,12.310,0.118,-1.448,0.031
```

采集完成后请**手工归档**到 `02_采集数据/telemetry/`（该目录已被 `.gitignore` 排除，不会上传）。

## 7. 使用注意

1. **同名 ID 上下行语义不同**：如 `0x11` 上行是"规划位置"，下行是"位置指令"；
   `0x13` 上行是"规划速度"，下行是"力矩指令"。请以第 4 节对照表为准。
2. **参数 ID 空间是扁平的**，M1/M2/传感器共用一套 ID，不存在"每台电机一套 ID"。
3. **协议调试页的 `启动电机 / 停止电机` 操作的是 M1（IO `0x01`）**，
   不是系统启停；系统启停只在电机页的 `系统启动 / 系统停止`（IO `0x0A`）。
4. **未定义 ID 不会被解析进字典**：遥测表格只显示字典内的行，多余 ID 不会出现在表格中，
   但**会出现在 CSV 列里**（列名写作 `0x??`）。
5. 所有 `writable = true` 的参数都会出现在协议页的"Float 写入 / 批量写入"下拉框中；
   只读参数（传感器、IMU）不会出现在下拉框里。
6. **`0x0B` / `0x1D` 读写不同义**（上行 = 虚拟轨迹角度，下行 = T 波速度），详见 §3.1 的注释。
7. 康复页两张图已改为「轨迹跟踪视图」：绿线是**上位机本地生成**的参考轨迹，
   **不是** `0x0B`/`0x1D`。`0x0B`/`0x1D` 仍照原样接收/记录，可用对应复选框单独查看（紫色）。
8. 本字典中标注「已实现」的条目对应 2026-10-16 版本的 `Uart_controller.exe`；
   若你手头的 exe 早于该日期，则看不到这些控件。
