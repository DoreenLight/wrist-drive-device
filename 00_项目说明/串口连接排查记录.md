## 2. 设备与端口识别

### 2.1 设备身份

```
硬件 ID : USB\VID_1A86&PID_55D2
序列号  : 5B14235030
芯片    : 沁恒 CH342（高速 USB 转双串口）
厂商    : 南京沁恒微电子（WCH）
```

### 2.2 两个端口的由来

设备插入后系统出现**两个**串口，这是芯片特性决定的，不是异常：

```
USB-Enhanced-SERIAL-A CH342 (COM12)     接口 MI_00
USB-Enhanced-SERIAL-B CH342 (COM13)     接口 MI_02
```

原因：CH342 是一片 **USB 转双串口** 桥接芯片。对 Windows 来说它首先是一个 USB 复合设备
（`USB\VID_1A86&PID_55D2`），内部再暴露**两个独立串口接口**（`MI_00`/`MI_02`），
每个接口各自绑定一次驱动、各自分配一个 COM 号。所以插入一次 = 多出两个 COM 口。

### 2.3 编号（COM12 / COM13）是怎么来的

- COM 号是 **Windows 分配的**，不是设备固定属性。它取决于插入那一刻系统里哪些编号空着，
  所以换电脑、或先插了别的串口设备，编号就会变。
- 但 Windows 会按设备的**序列号**（这里是 `5B14235030`）记住上次分配结果，
  因此在**同一台电脑、同一个 USB 口**上重插，编号通常稳定不变。
- 所以「COM13」本身没有任何特殊性，它只是**这台电脑给 B 路分配到的编号**。

### 2.4 为什么协议口在 B 路而不是 A 路

CH342 的 A、B 两路走线接到哪里，由**设备硬件设计**决定，芯片和驱动都无法得知。
实测结果：

| 端口 | 现象 |
|---|---|
| COM12（A 路） | 对所有探测**完全静默**，一个字节都没有 |
| COM13（B 路） | 能正常应答 PING |

结论：本设备的 MCU 协议串口接在 **B 路**。A 路要么未连接，要么接的是别的子系统
（例如调试口），不响应本协议。

## 4. 波特率：作用与实测确认

### 4.1 波特率是什么

波特率 = **每秒传输的符号数**。在 UART（异步串口）里，一个符号就是一个二进制位，
所以波特率实际就是**位速率（bit/s）**。

- **它决定每一位在线上持续多久**：位宽 = 1 / 波特率。
  例：230400 时，1 位 ≈ **4.34 µs**，一个 10 位字节帧（1 起始 + 8 数据 + 1 停止）≈ **43.4 µs**。
- **收发双方必须使用一致的波特率**。接收方靠起始位的下降沿同步，然后按约定的位宽
  在每一位的**中间**采样。两端速率不一致时，采样点会逐位漂移，漂出位窗口就产生误码。
- **容差很小**：一个帧内累积误差一般要小于半个位宽（≈ 5%）。实际工程上建议控制在
  **±2%～3%** 以内，所以用的都是 9600 / 115200 / 230400 这类双方都能精确分频的值。

### 4.2 它在哪一层生效

波特率属于**物理层参数**，和作用在它之上的自定义帧协议是两回事：

| 层面 | 谁在起作用 |
|---|---|
| PC 侧 | CH342 芯片内部的 UART 波特率发生器（由 USB 驱动下发的配置） |
| 设备侧 | MCU 的 USART/UART 外设，由芯片时钟分频得到 |
| 中间 | 只是电线上的电平与时间关系，协议帧内容与它无关 |

所以波特率不对时，**不是"数据内容错了"，而是根本读不出正确的比特**——
表现通常是收不到任何数据，或收到满屏乱码。

### 4.3 本设备的实测确认

扫描结果（`COM13`，每次单独发一个 PING）：

| 波特率 | 设备是否应答 |
|---|---|
| **230400** | ✅ 应答（`ACK` 帧校验通过） |
| 9600 / 19200 / 38400 / 57600 / 115200 / 460800 / 921600 | ❌ 完全无应答 |

值得强调：其他速率下是**完全无任何字节**，而不是收到乱码。这恰好反证了固件波特率就是 230400——
因为波特率不对时，PC 发出的 PING 被 MCU 解成无效帧而**直接丢弃**，MCU 自然什么都不回。

**结论：固件波特率 = 230400，帧格式 8N1，无流控。**

## 5. 协议层握手：成功

`COM13 @ 230400 8N1` 下，设备对 PING 返回了完全合法的应答帧，多次复现：

```
6C 67 01 83 84 08 ED
│  │  │  │  │  │  └─ END      = 0xED  ✓
│  │  │  │  │  └──── SUM      = 0x08  ✓  (LEN+CMD+载荷 = 1+0x83+0x84 = 0x108)
│  │  │  │  └─────── 应答命令 = 0x84  = PING
│  │  │  └────────── CMD      = 0x83  = ACK

│  └──────────────── SYNC_L   = 0x67
└─────────────────── SYNC_H   = 0x6C
```

说明上位机与设备之间的**协议实现对得上**，通信链路在电气和协议两侧都已经打通。

## 6. 遗留问题：回帧误码率高

### 6.1 现象

反复单发 PING，**只有一部分应答是合法的**，多数到达的帧是损坏的：

```
6C 67 01 83 84 08 ED   ← 合法
6C 67 01 00 44 00 00   ← 损坏
6C 67 01 00 85 98 00   ← 损坏
6C 67 01 00 E8 03 00   ← 损坏
```

规律：帧头 `6C 67 01` **始终正确**，但之后的 `CMD` 变成 `00`、`SUM` 与 `END` 也变成 `00`。

### 6.2 字节到达时序

理论值：230400 下每字节 ≈ 43 µs，7 字节帧 ≈ 304 µs。

| 帧 | 首末字节总耗时 | 字节间隔 |
|---|---|---|
| 合法帧 | 948 µs | 199 / 227 / 242 / 152 / 81 / 47 µs |
| 损坏帧 | 600 ～ 7886 µs | 出现 **500 µs、5498 µs** 等异常停顿 |

损坏帧存在远超正常值的字节间停顿，说明**发送过程中被中断、节奏不稳**，
不是单纯的采样点漂移。

### 6.3 已排除的可能

| 假设 | 排除依据 |
|---|---|
| 上位机软件问题 | 用 **.NET `SerialPort`** 与 **Qt `QSerialPort`** 两套完全不同的客户端测试，结果一致 |
| CH342 驱动问题 | 驱动签名有效、设备无错误码、两个端口都能正常打开收发 |
| DTR/RTS 电平干扰 | 置位与不置位、打开前/打开后设置，四种组合表现一致 |
| 选错端口 | 已确认协议口在 B 路（COM13） |
| 波特率选错 | 已确认 230400，且其他速率完全无应答 |

### 6.4 判定

问题定位在**设备侧 MCU 的串口发送环节**（发送被中断 / 时序不稳 / 信号完整性），
属于固件或硬件范畴，**无法从 PC 侧修复**。

## 8. 建议的后续排查方向（按优先级）

1. **设备供电** —— USB 只供通信，MCU/电机是否单独供电？电压是否达标、有无波动。
2. **共地** —— 电机电源地与 USB 地是否可靠共地（此类问题的头号元凶）。
3. **固件发送时序** —— MCU 的串口 TX 是否被长时间关中断打断（例如 TX 使用阻塞发送、
   或在临界区内位操作）。
4. **降波特率对照** —— 把固件串口改为 115200 再测。
   若 115200 稳定，说明是时钟裕量或信号完整性问题；**这一条对定位最有价值**。
5. **线缆与走线** —— 换短一些、带屏蔽的线，避开电机线束。
6. **硬件走线** —— 确认 CH342 的 B 路 RX 走线是否与其它信号共用或受干扰。

## 9. 复现方法（供后续核对）

1. 设备管理器确认存在 `USB-Enhanced-SERIAL-B CH342 (COM13)`；
2. 用任意串口工具打开 **COM13 @ 230400 8N1**；
3. 发送十六进制 `6C 67 00 84 84 ED`（PING 帧）；
4. 观察回复：应收到 `6C 67 01 83 84 08 ED`，但会夹杂损坏帧。

> 也可直接使用上位机：**协议调试页 → COM13 / 230400 → PING**。
