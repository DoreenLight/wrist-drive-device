# 术语与名词说明

本文解释本项目涉及的**驱动、通信、电机、康复、传感器**各类名词，
帮助第一次接触本设备的人看懂上位机界面与文档。

> 名词释义分两类标注：
> - **已确认**：来自本项目源码 / 协议定义 / 本机实测；
> - **行业通用**：代码中未直接说明，按行业惯例解释，仅供参考。

# 一、驱动（Driver）是什么

## 1.1 概念

**驱动程序是一段运行在操作系统内核或用户态、专门负责"翻译"硬件与操作系统之间语言的软件。**

操作系统并不认识每一款硬件。以本项目为例：Windows 天生不认识"沁恒 CH342 芯片"，
也不知道怎么通过 USB 与它交换数据、怎么把它变成一个有 COM 号的串口。
这些工作全部由**驱动**完成。

可以这样理解三者关系：

```text
上位机程序 (Uart_controller.exe)
        ↓  调用标准接口 QSerialPort / CreateFile("COM13")
操作系统 (Windows)
        ↓  调用驱动提供的接口
驱动程序 (CH343SER / CH343S64.SYS)
        ↓  按 USB 协议与芯片对话
硬件 (CH342 芯片 → MCU)
```

**关键点**：上位机只认"COM 口"这个标准概念，**完全不知道自己接的是什么芯片**。
它能不能用上设备，取决于驱动有没有把设备"变成"一个 COM 口。

## 1.2 为什么必须装驱动

不装驱动的后果，本项目就真实发生过（见 `使用手册_连接与采集.md`）：

| 状态 | 结果 |
|---|---|
| 未装驱动 | Windows 只把设备识别成"未知设备 / 通用 USB 设备"，**不生成任何 COM 口** → 上位机端口列表里根本没有这个设备，**完全无法通信** |
| 已装驱动 | 设备被正确识别为两个串口，得到 COM12 / COM13 → 上位机可以正常打开端口通信 |

## 1.3 驱动在 Windows 上的组成

一次串口驱动安装，会在系统里落下这几样东西：

| 组成 | 作用 | 本项目的实际内容 |
|---|---|---|
| `.inf` 文件 | 驱动安装信息：声明本驱动支持哪些硬件 ID、装哪些文件、注册什么服务 | `ch343ser.inf`（发布名 `oem153.inf`），声明支持 `USB\VID_1A86&PID_55D2&MI_00` 等 |
| `.sys` 文件 | 真正的驱动二进制，实际处理数据收发的内核模块 | `C:\Windows\System32\drivers\CH343S64.SYS` |
| 驱动库（DriverStore） | Windows 的驱动仓库，原样保存安装包 | `C:\Windows\System32\DriverStore\FileRepository\ch343ser.inf_amd64_...` |
| 系统服务 | 让内核能加载 .sys 的注册项 | `CH343SER_A64`（按需启动，指向 `CH343S64.SYS`） |
| 数字签名 | 证明驱动来源可信、未被篡改 | Valid，签发者 *Microsoft Windows Hardware Compatibility Publisher*（WHQL 认证） |

> 驱动是"安装一次、长期有效"的：装好之后，以后插拔设备都不需要再装。

## 1.4 与本项目无关但容易混淆的驱动类型

| 类型 | 例子 | 说明 |
|---|---|---|
| USB 转串口驱动 | CH343SER、CP210x、FTDI | **本项目属于这一类** |
| USB 设备类驱动 | `usb.inf` | Windows 自带的通用 USB 驱动。它只能把设备认成"USB 复合设备"，**不会生成 COM 口**。本项目未装 CH343SER 时，设备就是停在这一层 |
| 显卡/网卡驱动 | — | 与本项目无关 |

# 二、CH342 驱动是干什么的

## 2.1 CH342 是什么

**已确认**（本机实测）：

```
芯片      : 沁恒 CH342
厂商      : 南京沁恒微电子（WCH）
类型      : 高速 USB 转 双串口 桥接芯片
硬件 ID   : USB\VID_1A86&PID_55D2
本机序列号: 5B14235030
```

它做的事情很单一：**把 USB 数据包和 UART 串口电平互相转换**，让只有 USB 接口的电脑
能像使用传统串口一样与 MCU 通信。

```text
电脑 USB 口  ←→  CH342  ←→  MCU 的 UART (TX/RX)
```

注意：**CH342 只是"翻译官"，它不参与控制逻辑**。电机怎么动、康复怎么做、
数据怎么算，全部由 MCU（下位机）里的固件决定。

## 2.2 为什么要用 CH342 而不是普通串口

现在的笔记本基本都没有传统 9 针串口（DB9），只有 USB。
所以设备侧用一颗 USB 转串口芯片，把 MCU 的 UART 暴露成 USB，电脑插上就能用。

## 2.3 为什么它需要专门的驱动

USB 设备有成千上万种，Windows 不可能内置所有厂商的通信方式。
CH342 使用沁恒自己的 USB 通信格式，必须由沁恒提供的驱动来解析。
这类驱动叫 **VCP 驱动（Virtual COM Port，虚拟串口驱动）**——
它的核心任务就是：**把 USB 设备"变成"一个普通 COM 口**。

装好之后，在上位机看来，这个 USB 设备和一个 90 年代的物理串口没有任何区别。

## 2.4 本项目实际安装的驱动

| 项目 | 值 |
|---|---|
| 驱动包 | `ch343ser.inf`（沁恒官方，发布名 `oem153.inf`） |
| 版本 | 2.1.2025.07 |
| 驱动文件 | `CH343S64.SYS` |
| 服务名 | `CH343SER_A64` |
| 签名 | WHQL（微软硬件兼容性认证） |
| 装入时间 | 2026-10-14 21:40 |

## 2.5 一个芯片、一个驱动包、多个型号

**`CH343SER` 是沁恒这一代 USB 转串口芯片的通用驱动包**，一份驱动同时支持多种型号：

| 型号 | 串口数量 | 本驱动是否支持 |
|---|---|---|
| CH342 | 2 | ✅ |
| CH343 | 1 | ✅ |
| CH344 | 4 | ✅ |
| CH347 | 1~2 | ✅ |
| CH9102 / CH9101 / CH9103 / CH9104 | 1~4 | ✅ |

所以「CH342 的驱动」和「CH343 的驱动」是**同一个文件**，名字叫 CH343SER 不代表只能用于 CH343。

## 2.6 ⚠️ 与 CH341SER 的区别（常见踩坑点）

网上搜"CH34x 驱动"，最容易下到的是 **`CH341SER`**。它和本项目**不通用**：

| 驱动包 | 对应芯片 | 本项目是否适用 |
|---|---|---|
| **CH343SER** | CH342 / CH343 / CH344 / CH347 / CH910x | ✅ **需要的就是这个** |
| CH341SER | CH340 / CH341 | ❌ 不适用 |

不知道芯片型号时的判断方法：看设备管理器里的硬件 ID——

- `VID_1A86` + `PID_55D2 / 55D3 / 55D4 / 55D5 ...`（`55xx` 段）→ **CH343SER**
- `VID_1A86` + `PID_7523 / 5523` → CH341SER

## 2.7 一个设备、两个 COM 口（双串口原理）

CH342 有**两条独立的 UART 通道**。对 Windows 来说：

```text
一个 USB 复合设备  USB\VID_1A86&PID_55D2
├─ 接口 MI_00  →  通道 A  →  分配一个 COM 号（本机为 COM12）
└─ 接口 MI_02  →  通道 B  →  分配一个 COM 号（本机为 COM13）
```

所以**插一次会出现两个 COM 口**，这是正常现象。

- 两个口**彼此完全独立**，可以同时打开、互不干扰；
- 哪条通道接到 MCU 的哪个串口，由**设备硬件接线**决定，驱动和软件无从得知；
- 本项目实测：**协议通信走 B 路（COM13）**，A 路（COM12）无应答；
- COM 号是 Windows 分配的，会随插入环境变化，判断依据应是名字里的 `-A` / `-B`，而不是死记编号。

# 三、通信与串口相关名词

| 名词 | 含义 |
|---|---|
| **上位机** | 运行在 PC 上的控制软件，即本项目 `01_上位机程序` 编译出的 `Uart_controller.exe` |
| **下位机 / MCU** | 设备内部的单片机，负责实时控制电机、采集传感器、执行康复动作 |
| **串口 / COM 口** | 上位机与下位机之间的通信通道 |
| **VCP（虚拟串口）** | USB 设备经驱动转换后呈现出的 COM 口，与物理串口在使用上无差别 |
| **波特率** | 位速率（bit/s），决定每一位在线上持续多久。**两端必须一致**，详见 `使用手册_连接与采集.md` |
| **帧（Frame）** | 协议的最小消息单位，本项目格式为 `6C 67 LEN CMD 载荷 SUM ED` |
| **载荷 / Payload** | 帧中承载实际数据（参数 ID + 数值）的部分 |
| **SYNC** | 帧头同步字节 `0x6C 0x67`，用于在字节流中定位帧的起点 |
| **SUM（校验和）** | 帧内校验值，接收方重新计算并比对，用于发现传输错误 |
| **END** | 帧尾定界字节 `0xED` |
| **PING** | 通信测试命令，设备应回应 `ACK`。**不涉及任何电机动作，可安全使用** |
| **ACK** | 应答帧，表示设备已收到并处理某条命令 |
| **IO_REPORT** | 设备主动上报的 IO 状态 |
| **遥测 / TELEMETRY** | 设备周期性上传的运行数据（角度、速度、力矩、力传感器等） |
| **TX / RX** | 发送线 / 接收线。交叉连接（A 的 TX 接 B 的 RX）才能通信 |
| **GND** | 地线。**必须共地**，否则通信不稳定 |
| **DTR / RTS** | 串口的两个控制信号线。若被接到 MCU 的复位/BOOT 脚，可能影响 MCU 运行 |

# 四、电机相关名词

本项目控制**两个电机**，在代码和界面中分别叫 **M1 / M2**。

| 名词 | 含义 |
|---|---|
| **M1** | 电机 1。由 MCU 的 **TIM2** 定时器控制，走 MCU 内部闭环（位置/速度/PWM） |
| **M2** | 电机 2。通过 **RS00** 总线（CAN 类伺服协议）控制，是一个独立的伺服驱动器 |
| **TIM2 控制循环** | MCU 内部的定时中断控制循环。**必须"系统启动"后才会运行**，否则电机不动作 |
| **RS00** | M2 所用伺服驱动器的通信协议/型号标识 **（行业通用，代码未说明）** |
| **运控** | M2 的一种运行模式，由上位机持续下发位置/速度/力矩运行 **（行业通用）** |
| **CSP** | Cyclic Synchronous Position，周期同步位置模式，M2 的一种运行模式 **（行业通用）** |
| **PID** | 经典闭环控制算法，用比例(P)、积分(I)项修正偏差。M1 使用 |
| **Kp** | PID 的比例系数：偏差越大出力越大，过大易振荡 |
| **Ki** | PID 的积分系数：消除稳态误差，过大易超调 |
| **Kd** | 微分系数：抑制超调。M2 面板提供该参数 |
| **PWM 占空比** | 用脉冲宽度控制电机平均电压的方式，`M1 控制模式` 中的"PWM 测试"即此用途 |
| **规划位置** | 电机驱动器**期望**到达的位置（指令值） |
| **实际位置** | 电机**当前真实**的位置（编码器反馈值） |
| **规划速度 / 实际速度** | 同上，分别是期望速度与实测速度 |
| **力矩** | 电机输出的旋转力矩，单位 N·m |
| **电流限制** | 限制电机最大电流，用于保护电机与驱动器 |
| **最大速度** | 允许的速度上限（°/s） |
| **机械零点** | 把当前位置定义为机械原点（0°）。**会影响之后所有位置控制，慎用** |
| **清除故障** | 清除驱动器的故障标志。**可能掩盖真实问题，慎用** |
| **使能（Enable）** | 让驱动器输出力矩、可以受控运动；未使能时电机自由（可被手动转动） |

# 五、康复相关名词

本项目面向**腕关节康复**，提供两类康复模式：

## 5.1 被动康复（设备带着人动）

设备按预设轨迹带动腕关节往复运动，适用于关节活动度训练。

| 参数 | 含义 |
|---|---|
| **最小角度 / 最大角度** | 往复运动的两个端点（°），即轨迹的行程范围 |
| **循环次数** | 往复多少个来回后结束 |
| **T 波轨迹** | 被动康复使用的虚拟往复轨迹（代码中 `T波虚拟轨迹`）。名称来自其随时间呈 T 形/三角波状变化的形态 **（代码未说明，按命名推断）** |

## 5.2 主动康复（人主动发力，设备提供阻力/助力）

设备不主动带动，而是根据力传感器反馈施加阻力或助力，鼓励用户主动运动。

| 参数 | 含义 |
|---|---|
| **主动极限角 1 / 2** | 主动运动允许到达的两个边界角度（°），超出即受限 |
| **停顿时间** | 到达极限角后的停留时间（s） |
| **Tmax** | M1 主动康复的最大力矩（N·m） |
| **Fmax** | M2 主动康复的最大力（N） |
| **刚度 k** | 阻抗控制的刚度参数：越大越"硬"，需要越大力才能移动 |
| **T 波速度** | 主动康复轨迹的运动速度（°/s） |

## 5.3 腕关节解剖方向

| 名词 | 含义 |
|---|---|
| **掌屈 / 背屈** | 手掌向掌心侧弯曲 / 向手背侧弯曲。对应力传感器的 **Fy** 方向 |
| **尺偏 / 桡偏** | 手腕向小指侧偏移 / 向拇指侧偏移。对应力传感器的 **Fz** 方向 |

> 界面上 M2 主动康复的"模式"下拉框就是在这两个方向之间选择，设备据此决定用哪个力分量做闭环。

## 5.4 被动/主动康复里，电机到底在干什么

### 先分清两个模式的本意

| 模式 | 谁发力 | 设备的角色 |
|---|---|---|
| **被动康复** | **设备** | 沿着轨迹带动你的腕关节走，**你是放松的、不主动发力** |
| **主动康复** | **你自己** | 根据你偏离目标的多少 + 力传感器读数 + 刚度 k，给**助力或阻力** |

> ⚠️ 常见误解：如果“你的手带着机器动”，那不是被动康复，
> 而是主动康复（或在不该动的时候强行带动设备，俗称“抢动”）。
> 被动康复时你主动对抗电机是**不安全**的：电机会反向对抗（过流、发热），
> 也可能突然被你触发出力。

### 电机是否出力 / 是否耗电：分三种情形

关键前提：**电机“出力”与“是否转动”是两回事**。伺服装着不动、只是保持位置时，
也在通电出力、也在耗电（对抗重力时尤其明显）。

| 情形 | 电机在做什么 | 耗电？ | 手带动机器时的手感 |
|---|---|---|---|
| **未使能**（伺服关闭） | 不出力，线圈基本不供电 | 几乎不耗 | 只有机械阻力：减速箱摩擦、齿槽转矩、转动惯量，以及轻微反电动势制动 |
| **使能 + 位置闭环**（被动康复） | 死盯设定角度，偏离就反向出力拉回 | **耗电**（保持位置也耗） | 你在“推一个被固定住的旋钮”：**越偏越硬**；你正功，电机负功 |
| **使能 + 力矩/阻抗模式**（主动康复） | 按“偏离量 × 刚度 k” + 力限（Tmax/Fmax）给助力或阻力 | **耗电** | 你顺着它时**省力**（电机做正功），逆着它时**费力** |

所以“手带动机器时电机是否做功”**不能一概而论**，取决于：

- 伺服**是否使能**；
- 处于**位置环**还是**力矩/阻抗环**；
- 你带动的方向与设定轨迹是**同向**（电机在制动，做负功）还是**反向**（电机在帮忙，做正功）。

### 既然手已经能带动机器，为什么还要设备参与

因为目的**从来不是“把东西转起来”**，而是下面五件事——这些事靠手自己做不到：

1. **阻力/助力可调**：训练强度要能按康复处方调（刚度 k、Tmax/Fmax）；
   只靠手带，设备就只是一付带摩擦的支架；
2. **限位与安全**：极限角、速度上限、行程范围由设备强制约束，防止过度活动造成二次损伤；
3. **轨迹约束**：必须按规定的路径和节奏走（防止代偿动作、偷懒或发力不对），
   这就是 `轨迹输入` 存在的临床意义；
4. **量化评估**：持续采集角度、力矩、力（六维力）→ 可量化康复进展，这是“手工掰手腕”无法提供的；
5. **力量不足时补足**：肌力很弱的患者，光靠自己根本动不到目标位置，需要设备助力。

一句话：**设备不是在“帮你转”，而是在“管控你怎么转”**——
可控的阻力、可控的行程、可控的节奏、可量的数据。

# 六、传感器相关名词

## 6.1 DR304 六维力传感器

装在腕部接口处的**六维力/力矩传感器**，用于测量人施加在腕部的力和力矩。

| 符号 | 名称 | 单位 | 含义 |
|---|---|---|---|
| **Fx** | X 向力 | N | 沿 X 轴的推力/拉力 |
| **Fy** | Y 向力 | N | 沿 Y 轴的力（对应掌屈/背屈方向） |
| **Fz** | Z 向力 | N | 沿 Z 轴的力（对应尺偏/桡偏方向） |
| **Mx** | X 向力矩 | N·m | 绕 X 轴的扭矩 |
| **My** | Y 向力矩 | N·m | 绕 Y 轴的扭矩 |
| **Mz** | Z 向力矩 | N·m | 绕 Z 轴的扭矩 |

| 名词 | 含义 |
|---|---|
| **六维** | 3 个方向的力 + 3 个方向的力矩，共 6 个分量 |
| **力传感器归零** | 把当前受力定义为 0，消除安装应力与自重偏差。**会影响主动康复的力基准，慎用** |

## 6.2 IMU（惯性测量单元）

| 名词 | 含义 |
|---|---|
| **IMU** | Inertial Measurement Unit，惯性测量单元，测量姿态角 |
| **Roll（横滚）** | 绕前进轴的旋转角。**M1 的反馈角度即取此值** |
| **Pitch（俯仰）** | 绕横轴的旋转角 |
| **Yaw（偏航）** | 绕竖轴的旋转角 |
| **传感器角度 / 传感器电流** | 另一路角度/电流传感器读数（源码中存在，界面未直接显示） |

# 七、系统级操作名词

| 名词 | 含义 | 风险 |
|---|---|---|
| **系统启动 / 系统停止** | 启停 MCU 的 TIM2 控制循环。**不启动则电机不会动作** | 启动后电机可能立即响应既有指令 |
| **存入 Flash（FlashSave）** | 把 M1/M2 的 PID 等参数写入 MCU 非易失存储，**掉电后仍生效** | 参数错误会被持久化 |
| **Ping 心跳** | 仅做通信测试，不产生任何动作 | 无 |

# 九、开发注意事项（供二次开发参考）

1. **同一参数 ID 的上下行语义可能不同。** 例如 M1 面板的"速度目标""电流目标"输入框
   实际下发的是 `0x02` / `0x03`，而遥测字典里 `0x02` 是"反馈角度"、`0x03` 是"PID 输出"。
   使用时请以 `数据字典.md` 的"界面控件 ↔ 参数 ID"对照表为准。
2. **头文件中有若干已废弃的控件声明**（`treatModeCombo`、`treatAngleEdit`、`treatSpeedEdit`、
   `treatCyclesSpin`、`treatStartBtn`、`treatPauseBtn`、`treatStopBtn`）。它们只在
   `mainwindow.h` 中声明、在构造函数里初始化为 `nullptr`，实际界面并未使用——
   现在的康复面板是运行时构建的（最小/最大/循环 + 启动/停止）。
3. **康复页的"运行: 00:00:00"计时不会走。** 计时器 `treatTimer` 创建后未调用 `start()`，
   且 `treatRunning` 从未被置为 `true`，因此该显示恒为 `00:00:00`。这是已知限制，不是故障。
