## 0. 一句话结论

你要做的界面改造本身是清晰的、可行的；但**它卡住的真正原因不在界面**，而在两个被误解的前提：

1. 你以为绿色曲线是「上位机模拟」的 —— 实际上它是**下位机 MCU 算出来再传上来的**（浮点 ID `0x0B`）。所以「固定 5 周期」要改的是**轨迹来源**，不只是显示方式。
2. 你以为 🔵 轨迹输入和 🟠 反馈角度单位不同 —— 实际上**两者都是角度（°）**，互相关 0.99、只差约 0.25 s 相位。可以放在同一根 Y 轴上，不需要双 Y 轴。

这两条一旦确定，剩下的就是纯显示层改造。

## 2. 三条曲线到底是什么（源码 + 数据双重确证）

康复治疗页 · Motor1 康复曲线的三条线（`mainwindow.cpp:1835-1842`）：

```cpp
const uint8_t ids[]  = {0x01,        0x02,        0x0B};
const QColor  colors[] = {#1f77b4蓝,  #ff7f0e橙,   #2ca02c绿};
```

| 图例 | 颜色 | 浮点 ID | 名称（字典） | 单位 | 真实来源 | 实测证据 |
|---|---|---|---|---|---|---|
| 🟢 绿 | `#2ca02c` | `0x0B` | T 波虚拟轨迹 | **°** | **下位机 MCU 生成**上行的虚拟往复轨迹值 | CSV 列 `T波虚拟轨迹` = **±30.000**（164733） |
| 🔵 蓝 | `#1f77b4` | `0x01` | M1 轨迹输入 | **°** | 下位机回传的 PID 设定值（目标角度） | CSV 列 `M1 轨迹输入` = −30.10 … +30.10 |
| 🟠 橙 | `#ff7f0e` | `0x02` | M1 反馈角度 | **°** | 下位机回传的 IMU 实测 roll | CSV 列 `M1 反馈角度` = −25.88 … +25.29 |

### 2.1 必须纠正的两个认知（有源码依据）

**① 绿线不是上位机模拟的。**
上位机代码里**没有任何轨迹生成逻辑**（全项目 grep `qSin/sin/三角/虚拟/generate` 无命中）。
`0x0B` 是遥测 ID，上位机只做两件事：
- 接收 → 画曲线；
- 在「主动康复」面板写它（`mainwindow.cpp:1676-1683`，UI 标签写的是 `T波速度(°/s)` 默认 `30`）。

也就是说 `0x0B` 是一个**写=速度 / 读=轨迹值**的重载 ID（字典第 3.1 节也承认了这一冲突：`0x0B` 名字叫「T 波虚拟轨迹」，但界面控件对照表第 166 行写的是「主动 · T波速度 → `0x0B`」）。

**② `0x0B` 只在主动康复运行时才有值。**
| CSV | `T波虚拟轨迹` 取值范围 |
|---|---|
| telemetry_20260727_163615.csv | **恒 0.000** |
| telemetry_20260727_164609.csv | **恒 0.000** |
| telemetry_20260727_164733.csv | **−30.000 … +30.000**（干净三角波） |

→ 如果照现在的实现「绿线 = 接收 0x0B」，那么**程序一打开、实验还没跑的时候，绿线是 0，画不出完整的 5 周期**。
这是本次需求最关键的一条技术结论，直接引出 §3-④ 的决策。

## 3. 逐条回答你和 ChatGPT 卡住的 6 个问题

### ③ 🔵 轨迹输入和 🟠 反馈角度是什么关系？单位真的不同吗？

**结论：同一个物理量，同一个单位（°），只是「目标」与「实际」。不需要双 Y 轴。**

- 🔵 `0x01` = 下发给电机的**目标角度**（PID 设定值）
- 🟠 `0x02` = IMU 实测的**当前角度**
- 字典明确写：`0x01` 单位 `°`「下发给 M1 的目标角度（PID 设定值）」；`0x02` 单位 `°`「IMU 实测的 roll 角」

**定量证据**（`telemetry_20260727_163615.csv`，643 样本，41 s）：

| 指标 | 结果 |
|---|---|
| 两者互相关 | **r = 0.9904** |
| 最佳时移 | 5 个采样 = **0.24 s**（反馈滞后于目标） |
| 差值 均值 / 标准差 | **+0.204°** / **7.98°** |
| 差值 最大绝对值 | **11.53°**（出现在三角波换向的快速段） |
| 另一份 164609.csv | r = **0.9931**，时移 **0.32 s** |

→ ChatGPT 担心的「情况 B：轨迹输入是编码器脉冲」**不成立，可以排除**。
→ 但两者**不是同一条线**：0.25 s 的跟随滞后 + 换向处约 11° 的瞬时偏差，正是这类实验最想看的东西。所以**建议保留两个点（🔵 目标 + 🟠 实际）**，而不是只留反馈点。

### ① 五个周期的总时长是多少？

**程序里没有「周期时长」参数，它是用参数算出来的。**
M1 主动康复的 6 个参数（`mainwindow.cpp:1676-1683`，含界面默认值）：

| UI 标签 | 浮点 ID | 界面默认值 | 含义 |
|---|---|---|---|
| T波速度(°/s) | `0x0B` | **30** | 斜坡角速度 |
| 极限角1(°) | `0x0C` | **−30** | 一侧边界 |
| 极限角2(°) | `0x0D` | **+30** | 另一侧边界 |
| 停顿时间(s) | `0x0E` | **2** | 到达极值后停留 |
| Tmax(N·m) | `0x0F` | 5 | 最大力矩 |
| 刚度k | `0x10` | 10 | 阻抗刚度 |

**波形定义**：在极限角1 保持 `停顿` → 以 `T波速度` 升到极限角2 → 保持 `停顿` → 以 `T波速度` 降回极限角1 → 重复。

**按默认值算**：单周期 = `2 + 60/30 + 2 + 60/30` = **8 s** → **5 周期 = 40 s**

**实测对照**（`telemetry_20260727_164733.csv` 的 `0x0B` 列，716 样本 / 36 s）：

| 实测项 | 值 |
|---|---|
| 平台值 | **±30.000°**（精确） |
| 单侧保持 | **约 2.0 s** |
| 斜坡用时 | 60° 用 **约 1.4 s** → 速度 ≈ **43 °/s** |
| **单周期** | **≈ 6.7 – 6.9 s** |
| 该次实验 5 周期 ≈ | **34 s** |

→ **X 轴总时长不许硬编码**，必须现算：
`T = 5 × ( 2×停顿 + 2×(极限角2 − 极限角1) / T波速度 )`

### ② 五个周期是不是完全连续？

**不连续。停顿发生在每个极值点之后**（不是只发生在周期之间）。

实测 164733 的 `0x0B` 平台段：`−30 保持 2.1 s → 升 → +30 保持 1.8 s → 降 → −30 保持 2.1 s …`

→ 因为「周期」本身已经含 **2 个平台**，所以 X 轴只要按 §3-① 的公式算总长，平台就自动包含在内。不要额外再插停顿。

### ④ 绿色参考轨迹的生成算法要不要改？

**必须分两种情况选一个（这是本次唯一的架构级决策）：**

| 方案 | 做法 | 代价 | 能不能一打开就显示完整 5 周期 |
|---|---|---|---|
| **A. 本地生成（推荐）** | 上位机新增一个**纯本地**的三角波生成器，参数取现有面板输入 | 属于「新增」而非「只改显示」，但不碰下位机、不碰协议 | ✅ 能（离线可预览、可对比） |
| B. 冻结下位机 `0x0B` | 接收 0x0B，跑一遍后冻结/重放 | 改动最小 | ❌ 不能（未运行时 0x0B = 0） |
| C. A + B 可切换 | 默认 A，留一个下拉框切到 B | 多一点代码 | ✅ |

> ✅ **决策结果（2026-10-16）：采用方案 A —— 上位机本地生成参考轨迹。**
> 下位机 `0x0B` 只作为「实验数据」继续接收与记录，**不再作为绿线的数据源**。

理由：
- 未运行/脱机也能看到完整参考轨迹，符合「固定 5 周期参考轨迹」这句话的直觉；
- 多次实验可以用**完全相同的参考轨迹**，才谈得上对比不同参数下的跟踪效果；
- **不修改下位机、不修改协议、不修改现有控制逻辑**，风险最低。

⚠️ 注意：**上限「5」必须新做成参数**。因为主动康复面板里**没有循环次数参数**（`0x0A` 循环次数只属于被动康复）。所以 N 必须在本地生成器里自己定义。

### ⑤ 实验结束后怎么处理？

已定：**停在最右侧、保留最后一点、不自动循环**；点「开始 / 重新开始」才进入下一轮。

补充 3 条建议（已并入 §5.6 状态机）：
- 中途点「停止」→ 游标停在**当前位置**（不是跳到最右）；
- 「重新开始」时，参数不变则**参考轨迹逐点相同**（不重新随机）；
- 结束后曲线与点**冻结显示**，不要清空（便于截图 / 答辩）。

|---|---|---|
| 电机控制调试 | Motor1 实时遥测 | `0x01`蓝 `0x02`橙 `0x03`绿 `0x04`红 `0x05`紫 |

## 4. 现有绘图机制的硬约束（改之前必须知道，否则一定踩坑）

| 项 | 现状 | 源码位置 |
|---|---|---|
| 图对象 | `MotorChartCtx`（chart / axisX / axisY / series / buffers / checkboxes / time） | `mainwindow.h:171-179` |
| 建图 / 喂数 | `buildMotorChart()` / `feedMotorChart()` | `.cpp:2075` / `.cpp:2143` |
| 刷新率 | `mChartTimer` **50 ms（20 Hz）** | `.cpp:152-153` |
| **降采样** | 一批数据里**同 ID 只保留最后一帧**（`merged.insert`）→ 界面曲线是趋势图，**不是逐帧数据** | `.cpp:164-167` |
| 环形缓冲 | 每个 series **最多 200 点**，超出丢最旧 | `.cpp:2152` |
| X 轴 | `ctx.time` 每刷新 **+1**（单位是「刷新次数」，不是秒），窗口 `[time-200, time]` ≈ 10 s 滑动窗 | `.cpp:2157-2159` |
| Y 轴 | 每次刷新按**可见 series** 自适应（±15% 余量）→ 会随数据抖动 | `.cpp:2161-2174` |
| 初始可见性 | 所有曲线 `setVisible(false)`，靠复选框打开 | `.cpp:2104` |

**对改造的直接影响**：
1. 现在的 X 轴是「刷新次数」，**不是秒**。要做「时间游标」，必须换成真实时间轴。
2. 50 ms + 最后一帧 **会把点画错位**（你看到的点可能是 50 ms 前的旧值）。要做「当前点」必须**单独保存该批内的最新值 + 对应时间戳**。
3. Y 轴自适应会毁掉「固定参考轨迹」的稳定观感，必须改成固定范围。
4. 「历史实际轨迹」如果要做，200 点环形缓冲远不够（40 s 实验 × 20 Hz = 800 点），需要按时间戳另存。

## 5. 完善后的需求规格（建议定稿）

### 5.1 目标（一句话）

> 把康复治疗页的两张曲线改成「**固定 5 周期参考轨迹 + 时间游标 + 实时目标点/反馈点**」的轨迹跟踪视图。
> 通信协议、下位机、控制逻辑、数据记录**全部不动**。

### 5.2 数据层

| 编号 | 需求 |
|---|---|
| D-1 | 接收链路完全不变：`ProtocolWorker` 解析 `0x81` 遥测帧，230400 / 8N1 / 无流控 / B 路 |
| D-2 | 每个遥测样本记录**本地实验时间戳** `t = now − t_实验开始`，**不许用帧序号当 X 坐标** |
| D-3 | 保留现有 `mTelemetryQueue`，但**新增一路「原始样本」入口**给轨迹视图用：至少保存「本批内该 ID 的最后一个值 + 其时间戳」，避免 §4 的降采样错位 |
| D-4 | CSV 记录逻辑**不变**（`RecordFrame` / `m_recordBuffer` 一行不改） |
| D-5 | 参考轨迹参数读取优先级：面板输入框 → 空则用界面默认值（`0x0C=-30`、`0x0D=30`、`0x0E=2`、`0x0B=30`） |
| D-6 | 数值合理性过滤（**必须做**，理由见 §6.1）：非有限值、或 `|angle| > |极限角| × 1.5` 的样本**丢弃并标记**，否则 M2 的橙点会飞到图外 |

### 5.3 参考轨迹（绿线）

| 编号 | 需求 |
|---|---|
| R-1 | 点「开始」时**一次性生成**整条 N 周期轨迹并缓存为 `QVector<QPointF>{t, angle}`，全程**不重算、不滚动、不缩放** |
| R-1b | 周期数 N 由新增的「周期数」输入框给出，**可调，默认 5**，范围 1–20 |
| R-2 | 波形 = 与下位机 T 波一致的分段线性三角波：`保持(极限角1, 停顿) → 匀速斜坡 → 保持(极限角2, 停顿) → 斜坡回极限角1`，重复 N 次 |
| R-3 | `T = N × (2×停顿 + 2×(极限角2−极限角1)/T波速度)`，N 默认 **5**（可调） |
| R-4 | 起点定义：`t=0` 从**极限角1 的保持段开始**（与实测一致：绿线一开始就平在 −30） |
| R-5 | 重新开始实验时，参数不变则轨迹**逐点相同**（可复现，便于对比实验） |
| R-6 | X 轴**固定** `[0, T]` 并显示秒刻度；Y 轴**固定** `[极限角1−5°, 极限角2+5°]`（默认 −35…35），**不随数据自适应** |
| R-7 | 未开始实验时也要能显示完整参考轨迹（离线预览） |

### 5.4 时间游标

| 编号 | 需求 |
|---|---|
| C-1 | 一条贯穿绘图区上下的竖直线，`X = 当前实验时间 t`（0 → T） |
| C-2 | 只从左向右单向移动；**不受 Y 轴缩放影响** |
| C-3 | 游标与实时点**必须用同一个 t**，不许一个用系统时间、一个用数据到达时间 |
| C-4 | 用 `QLineSeries` + 两个点（或 `QGraphicsLineItem`）实现，`setZValue` 置顶，不被数据点遮挡 |

### 5.5 实时点

| 编号 | 需求 |
|---|---|
| P-1 | 游标上显示 **2 个点**：🔵 目标角度（`0x01`）/ 🟠 实测角度（`0x02`）；Motor2 对应 `0x11` / `0x12` |
| P-2 | 点为**最近一次收到的该 ID 值**，`X = 收到该值时的实验时间`；超过 **300 ms** 未更新 → 保持最后值但显示为空心/灰色（表示断流） |
| P-3 | 历史轨迹按接收时间**持续累积并扫描式绘制**（见 §11.1）；开关为「显示历史轨迹」复选框，**默认开**；取消勾选只隐藏不丢数据 |
| P-4 | 增加数字读数区：`当前时间 t`、`参考角度`（绿线在 t 处的值）、`实测角度`、**跟踪误差 = 参考 − 实测**，Motor1 / Motor2 各一组 |

### 5.6 状态机

```
初始（可预览完整参考轨迹）
   │ 点「开始 / 重新开始」
   ↓
生成参考轨迹 → t = 0 → 游标归零 → 清空历史实际点
   ↓
运行中：t 增长 → 游标右移 → 🔵/🟠 点更新 → 读数刷新
   ↓  t ≥ T
结束：游标停在最右、保留最后一个点、停止更新（不清空）
   │ 点「重新开始」
   ↓
```

## 6. 动手前必须先知道 / 先解决的 2 个现实问题

### 6.1 遥测帧 100% 校验失败 —— 这是真 bug，不是噪声（已定位到大概方向）

我把 `build/Desktop_Qt_6_8_2_MinGW_64_bit_Release/error_frames.txt`（3.2 MB，**9392 条**）逐条解析：

| 分析项 | 结果 |
|---|---|
| 记录类型 | **全部** `[chk_fail]`，没有一条通过 |
| 命令码分布 | `0x81` 遥测帧 **9385** 条，`0x00` 7 条 |
| 帧长 | **全部** `LEN=0x5B=91` → 整帧 97 字节，`count=0x12=18` 组 |
| 逐字节统计 | 字节 0/1/2/96 **完全恒定** = `6C 67 5B ED` → 帧头 / 长度 / 帧尾**全对** |
| 上位机 calcSum 与文档公式 | **9392/9392 完全一致** → 上位机校验实现**正确** |
| 9 种备选校验公式命中率 | 最高仅 **0.67%** → **不是**「两端校验算法不一致」 |
| 损坏位置 | 集中在**载荷第 16–35 字节**（帧偏移 20–39）＝ 正好 `M1 Kp` / `M1 Ki` / `M2 规划位置` / `M2 实际位置` **四组的 id + 值** |
| 未损坏区 | `0x01 / 0x02 / 0x0B / 0x11 / 0x13..0x15 / 0x41..0x46 / 0x1D` 解出的值**全部合理** |
| 损坏区出现的怪值 | 反复出现 `58 01 00 20`（= `0x20000158`）与 `3B 34 00 08`（= `0x0800343B`）——分别是 **STM32 SRAM（0x2000_xxxx）和 Flash（0x0800_xxxx）地址**；同一位置在不同帧里时而是正常值（Kp=0.05、Ki=0.01），时而是这些地址 |

**判断**：帧同步、长度、上位机解析、校验算法**都没问题**；损坏集中在固定的一段且是**结构化**的（不是随机比特翻转），并混入 MCU 的 RAM/Flash 地址
→ **强烈指向下位机固件的遥测打包缓冲区竞争 / 未初始化**。不是电脑、不是 CH342 驱动、不是上位机代码。

**对本需求的影响**：
- ✅ 绿线 `0x0B`、蓝线 `0x01`、橙线 `0x02`（Motor1）**恰好都落在未损坏区** → 本次改造不受影响
- ⚠️ **Motor2 的橙点用 `0x12`（M2 实际位置），正在损坏区** → 会偶尔跳到 `3e-34` 这种垃圾值
  → 所以 §5.2 的 **D-6 数值合理性过滤是必需的**，不是可选项

| 真实遥测接入 | 现场实测期间（端口被打开、设备在上传）读数出现 `参考 -30.00°　目标 -31.65°　实测 -33.08°　误差 3.08°` → 本地参考 + `0x01`/`0x02` 实时样本链路打通 |
| 结束行为 | `t` 到达 40.0 后：状态 `已结束　T = 40.0 s`，读数后缀 `[已结束]`，游标停在最右，**不自动循环** |
| 重新开始 | 点「重新开始」后 `t` 回到 ~0 并继续运行；参考轨迹由纯函数按同一组参数生成 → 逐点相同 |
| 数值合理性过滤 | 每帧对非有限值或 `|angle| > |极限角|×1.5` 计数丢弃，读数显示「丢弃异常 N」 |
| 断流标记 | 运行中 >300 ms 无该 ID 数据 → 读数追加 `⚠ 实测断流 N ms`，该点变灰 |
| 电机页回归 | `buildMotorChart` / `feedMotorChart` / `mChartTimer` 对电机页两个 ctx 的调用序列未变 |

### 10.5 验证方式的局限（须知）

1. 上表「真实遥测接入」是**现场实测期间顺带观察到**的，不是可控复现的实验，没有重放脚本。
2. 「显示历史轨迹」与「显示下位机 0x0B/0x1D 原始」两个复选框**取消勾选后**的效果需要真实数据/交互才会显现，本轮**未逐项截图核对**（已在 §11.5 重新声明）。
3. 本轮验证**未下发任何电机/康复指令**，也**未做「开始实验」与真实康复同时运行的压力测试**。

## 11. 追加需求与实现（2026-10-16 第二轮）

用户在首轮验收后追加了两条需求，均已实现并验证。

### 11.1 追加需求 1：历史痕迹保留（扫描式实时绘图）

原实现只在游标上显示当前点；现改为把已收到的历史数据按时间顺序持续连接成曲线，
随游标从左向右逐步绘制出来（扫描式），同时保留竖直游标与当前点。

| 项 | 实现 |
|---|---|
| 历史数据追加 | `feedTrackerSample()` 中每帧把值追加到 `histTargetSeries` / `histActualSeries`，X = **接收时刻的实验时间**；**只在本帧真的收到该 ID 时才追加**，不拿上一帧的值凑点，避免伪造采样 |
| 默认开关 | 「显示历史轨迹」复选框**默认勾选**；取消勾选只隐藏、**不丢数据**（数据继续累积，重新勾选即恢复全貌） |
| 重新开始 | `applyReference(true)` 清空两条历史 series → 新一轮从空白开始重新扫一遍 |
| 点数上限 | `appendBounded()`：每条 series 上限 30000 点，超出后**成批**丢弃最旧点（防高采样率下无限增长，摊销代价 O(1)） |
| 图层顺序 | 参考轨迹改为**较粗的半透明绿带**（宽 3.5、α=150）并画在数据曲线**之下**：数据与参考重合时蓝/橙细线仍清晰可见，游标右侧尚未扫到的部分仍是完整绿线 |
| 当前点形状 | 🔵 目标 = **蓝色方形**（12 px）、🟠 实测 = **橙色圆形**（10 px）——两者重合时也能分辨 |
| 读数一致性 | 读数行的「目标」与历史蓝线同源（`0x01`/`0x11`），「实测」与历史橙线同源（`0x02`/`0x12`） |

### 11.2 追加需求 2：必须显示图例

| 项 | 实现 |
|---|---|
| 图例内容 | 固定三项：**参考轨迹（绿）/ 轨迹输入（蓝）/ 反馈角度（橙）**，名称由 `QAbstractSeries::setName()` 设置 |
| 排除项 | 时间游标、下位机原始轨迹、两个当前点**都不进图例**（否则会出现 6~7 项） |
| 位置与字号 | 图例置顶居中，字号与坐标轴刻度一致（高 DPI 下才不会挤掉刻度） |
| **全状态一致** | `refreshTrackerLegend()` 在「建图后 / 三个复选框切换后 / `applyReference()` 后」都会重新校正一次 marker 可见性 |
| 为什么必须显式校正 | Qt Charts 的图例 marker 会**跟随 series 可见性自动变化**（勾选框、清空数据、重新开始都会触发），这是"图例时有时无/条目变少"的常见原因 |
| 复选框改名 | 为避免与图例措辞混淆，三个复选框统一改为动词式：`显示参考轨迹` / `显示历史轨迹` / `显示下位机 0x0B 原始`（M2 为 `0x1D`） |
